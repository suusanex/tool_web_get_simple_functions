# Plan Kernel

## 目標

指定された検索日に対して、RAKU SPA 1010 神田のコラボレーションイベント状況を報告する、Azure Functions ベースの認証付き API を作成する。

この API は、検索日にアクティブなコラボレーションイベント（存在する場合）と、検索日以降の次のコラボレーションイベントを返す必要がある。情報源としては RAKU SPA / 関連する公開 Web 情報を使用し、テキストソースに対する Azure OpenAI の構造化抽出を利用する。この API は、Android ブラウザ、HTTP ショートカットアプリ、または将来的な軽量クライアントなどのモバイルクライアントから呼び出されることを想定しており、Azure App Service 認証/承認（Microsoft Entra サインイン）によってアクセスが保護される。

## 非目標（スコープ外）

*   今回のパスでは LLM による画像分析を実装しない。
*   今回のパスでは Playwright やブラウザ自動化を実装しない。
*   今回のパスでは RAKU SPA 1010 神田以外の施設をサポートしない。
*   今回のパスでは完全な Android ネイティブアプリケーションを構築しない。
*   今回のパスではプッシュ通知、LINE 通知、Teams 通知、メール通知を構築しない。
*   今回のパスでは Durable Functions オーケストレーションを実装しない。
*   今回のパスでは完全な管理 UI を実装しない。
*   認証が必要なページのスクレイピングは行わない。
*   決定論的な検証なしにモデル出力を権威あるものとして扱わない。
*   本 Plan には、完全なランタイムエビデンス、完全な統合テスト設計、最終的なランタイムコントラクト選定を含めない。

## 機能要件

### FR-001: 認証付き HTTP API

RAKU SPA 1010 神田のコラボレーションイベント状況を検索日に対してリクエストするために、モバイルまたはブラウザクライアントから呼び出し可能な HTTP API エンドポイントを提供する。

エンドポイントは Azure App Service 認証/承認（Microsoft Entra サインイン）によって保護されなければならない。未認証の呼び出し元にはイベントデータを返してはならない。

API は検索日を受け付ける必要がある。呼び出し元が日付を省略した場合、API は設定されたアプリケーションタイムゾーンにおけるサーバー側の現在日付を使用しなければならない。

### FR-002: 施設固有のイベント検索

実装は RAKU SPA 1010 神田に関するイベント情報のみを評価しなければならない。

実装は、ソースページで使用される一般的な施設名のバリエーションを認識しなければならない。少なくとも以下を含むこと：

*   `RAKU SPA 1010 神田`
*   `らくスパ 1010 神田`
*   `らくスパ1010神田`
*   `RAKU SPA 1010 KANDA`

### FR-003: 公式ソースの収集

実装は、公式または信頼性の高い公開ソースからイベント候補情報を収集しなければならない。

主要ソースは RAKU SPA 1010 神田の公式ニュースページである。候補ニュース項目は、以下のようなコラボレーション/イベントシグナルを用いて、記事タイトルおよび記事本文から特定されるべきである：

*   `コラボ`
*   `開催決定`
*   `スペシャルイベント`
*   `×極楽湯`
*   `×RAKU SPA`

実装は、公式キャンペーン/特設ページへの記事リンクが存在する場合、そのリンクを辿らなければならない。

実装は、関連する公式運営者の PR TIMES ページなど、信頼性の高い公開プレスリリースページを、公式ページから発見可能な場合や決定論的な検索/候補抽出で発見可能な場合に、補足ソースとして使用してもよい。

### FR-004: テキストのみの抽出入力

実装は、LLM 向けにテキストのみの抽出入力を構築しなければならない。

入力には、以下のような正規化された候補データを含めるべきである：

*   検索日
*   施設名およびエイリアス
*   ソース URL
*   ソース種別
*   記事タイトル
*   記事公開日（取得可能な場合）
*   抽出された表示テキスト
*   リンク先キャンペーンページ URL
*   リンク先キャンペーンページタイトル
*   リンク先キャンペーンページの表示テキスト
*   画像 alt テキスト（取得可能な場合）
*   検出された日付様の文字列
*   検出された会場様の文字列

今回のパスでは、実装は生の画像を LLM に送信してはならない。

### FR-005: Azure OpenAI 構造化抽出

実装は、テキストのみの候補入力からイベント候補を抽出するために Azure OpenAI を呼び出さなければならない。

モデル出力は固定の構造化スキーマを使用しなければならない。スキーマは以下の情報を表現するのに十分でなければならない：

*   タイトル
*   開始日
*   終了日
*   RAKU SPA 1010 神田が対象会場として確認されているか
*   ソース URL
*   エビデンススニペットまたはエビデンス参照
*   確信度
*   警告

実装は、プレーンな自由形式 JSON 出力よりも Azure OpenAI Structured Outputs を優先しなければならない。

### FR-006: LLM 抽出後の決定論的検証

実装は、LLM 出力を返す前に検証しなければならない。

検証は、以下の場合に候補を拒否またはダウングレードしなければならない：

*   開始日または終了日が欠落している
*   開始日が終了日より後である
*   ソース URL が欠落している
*   会場の一致が確認されていない
*   イベントがコラボレーション/特別キャンペーンイベントであることが明確でない
*   出力に候補入力に遡って追跡できない値が含まれている

検証は、不確実な結果を暗黙的に受け入れるのではなく、警告を生成しなければならない。

### FR-007: アクティブイベントおよび次回イベントの選択

指定された検索日に対して、実装は以下を選択しなければならない：

*   `activeEvent`: `startDate <= searchDate <= endDate` である確認済みコラボレーションイベント。存在しない場合は `null`
*   `nextEvent`: `startDate > searchDate` であり、`startDate` が最も近い将来の開始日である確認済みコラボレーションイベント。存在しない場合は `null`

複数の候補が重複する場合、実装は決定論的な順序付けを使用し、警告を含めなければならない。

### FR-008: 混雑フェーズ分類

レスポンスは、イベント開始日に基づいて混雑フェーズを分類しなければならない。

初期の高混雑ウィンドウは、イベント開始日から開始日＋2日間である。

レスポンスには少なくとも以下を含めなければならない：

*   `initialPeakDates`
*   `busyPhase`

許可される `busyPhase` の値：

*   `initial_peak`
*   `after_initial_peak`
*   `before_event`
*   `no_event`
*   `unknown`

### FR-009: API レスポンスコントラクト

HTTP API は安定したプロパティ名を持つ JSON レスポンスを返さなければならない。

レスポンスには以下を含めなければならない：

*   `facility`
*   `searchDate`
*   `generatedAt`
*   `activeEvent`
*   `nextEvent`
*   `warnings`
*   `sourceSummary`

各イベントオブジェクトには以下を含めなければならない：

*   `title`
*   `startDate`
*   `endDate`
*   `initialPeakDates`
*   `busyPhase`
*   `confidence`
*   `sourceUrls`

### FR-010: モバイルで読みやすい最小限の出力

エンドポイントはモバイルブラウザから直接利用可能でなければならない。

今回のパスでは JSON レスポンスが必須の出力である。コンパクトな人間が読みやすいテキストまたは HTML 表現は、コアスコープを拡大せず JSON コントラクトを弱めない場合にのみ追加してよい。

### FR-011: 可観測性と診断

実装は、シークレットをログに記録することなく、ソース抽出および LLM 抽出の障害をトラブルシューティングするのに十分な診断情報をログに記録しなければならない。

ログには以下を含めなければならない：

*   リクエスト相関 ID
*   検索日
*   ソース取得の成功/失敗
*   候補数
*   LLM 抽出の成功/失敗
*   検証警告
*   最終的なアクティブ/次回イベント選択状況

ログには Azure OpenAI API キー、Easy Auth トークン、Cookie、または完全な認証ヘッダーを含めてはならない。

### FR-012: 設定

実装は以下の項目を設定で管理しなければならない：

*   アプリケーションタイムゾーン
*   Azure OpenAI エンドポイント/デプロイメント/モデル設定
*   ソース URL
*   HTTP タイムアウト
*   最大ソースページサイズ
*   キャッシュ期間（キャッシュが実装される場合）
*   認証関連の環境前提

シークレットをハードコードしてはならない。

## 受入条件

### AC-001（FR-001 対応）

未認証の呼び出し元がデプロイ環境でイベントエンドポイントをリクエストした場合、Easy Auth の設定に従ってサインインにリダイレクトされるか、未承認レスポンスを受け取り、イベントデータは返されない。

### AC-002（FR-001 対応）

認証済みの許可ユーザーが有効な `date=YYYY-MM-DD` でエンドポイントをリクエストした場合、API は HTTP 200 とレスポンスコントラクトに一致する JSON ボディを返す。

### AC-003（FR-001 対応）

date パラメータが省略された場合、API は設定されたアプリケーションタイムゾーンの現在日付を使用したレスポンスを返し、選択された `searchDate` がレスポンスに含まれる。

### AC-004（FR-002 対応）

候補ソースにサポートされている RAKU SPA 1010 神田のエイリアスのいずれかが含まれている場合、実装はそれを施設の一致として扱うことができる。

### AC-005（FR-002 対応）

候補イベントが RAKU SPA 1010 神田を対象会場として確認していない場合、その候補は `activeEvent` または `nextEvent` として返されない。

### AC-006（FR-003 対応）

RAKU SPA 1010 神田の公式ニュースページにコラボレーション関連の記事が含まれている場合、ソース収集ステップはそれらの記事の候補レコードを生成する。

### AC-007（FR-003 対応）

候補記事が公式キャンペーンページにリンクしている場合、ソース収集ステップはそのリンクを辿り、リンク先ページの表示テキストを候補入力に含める。

### AC-008（FR-004 対応）

LLM 抽出リクエストはテキスト由来のデータとメタデータのみを受け取る。画像バイナリコンテンツや画像スクリーンショットは受け取らない。

### AC-009（FR-005 対応）

Azure OpenAI のレスポンスは、設定された構造化スキーマを通じてパースされる。モデルからの自由形式の散文は、成功した抽出結果として受け入れられない。

### AC-010（FR-006 対応）

モデルが無効な日付順序、ソース URL の欠落、または未確認の会場一致を持つイベントを返した場合、実装はそのイベントを最終的なアクティブ/次回の選択から除外し、警告を記録する。

### AC-011（FR-007 対応）

確認済みイベント期間内の検索日に対して、レスポンスにはそのイベントが `activeEvent` として含まれる。

### AC-012（FR-007 対応）

次の確認済みイベント期間より前の検索日に対して、レスポンスには最も近い将来の確認済みイベントが `nextEvent` として含まれる。

### AC-013（FR-007 対応）

アクティブなイベントがなく、既知の将来のイベントもない検索日に対して、`activeEvent` と `nextEvent` の両方が `null` であり、一致するイベントが見つからなかったことを示す警告またはソースサマリーがレスポンスに含まれる。

### AC-014（FR-008 対応）

`2026-05-28` に開始するイベントに対して、検索日が `2026-05-28`、`2026-05-29`、または `2026-05-30` の場合、`initial_peak` と分類される。

### AC-015（FR-008 対応）

`2026-05-28` に開始するイベントに対して、イベント期間内だが `2026-05-30` より後の検索日は `after_initial_peak` と分類される。

### AC-016（FR-009 対応）

JSON レスポンスには、イベントが見つからない場合でも、常に `facility`、`searchDate`、`generatedAt`、`activeEvent`、`nextEvent`、`warnings`、`sourceSummary` が含まれる。

### AC-017（FR-010 対応）

認証済みユーザーとしてモバイルブラウザからエンドポイントを開くと、デスクトップ専用のワークフローを必要とせずに JSON レスポンスが表示される。

### AC-018（FR-011 対応）

ソース取得または LLM 抽出が失敗した場合、どのフェーズで失敗したかを特定するのに十分な相関情報がログに含まれ、シークレットや認証トークンはログに記録されない。

### AC-019（FR-012 対応）

Azure OpenAI のエンドポイント、デプロイメント名、および資格情報は、ハードコードされた定数ではなく、設定またはマネージド ID 互換の設定を通じて提供される。

## 想定される実装スコープ

RAKU SPA 1010 神田のコラボレーションイベント状況に対して、1つの認証付き HTTP エンドポイントを公開する .NET isolated worker Azure Functions アプリケーションを実装する。

実装は、決定論的な Web/ソース処理と LLM 抽出を分離するべきである。ソースの取得と HTML/テキスト抽出は決定論的な C# ロジックで行うべきである。Azure OpenAI は、曖昧なテキストエビデンスの解釈と構造化候補抽出結果の返却のみを担当するべきである。

実装はモデル出力後に決定論的な検証を適用し、未検証の LLM 出力を直接返してはならない。

エンドポイントは Easy Auth サインインを通じたモバイルでの直接利用に適しているべきである。

最初の実装パスはライブリクエスト実行に焦点を当てるべきである。キャッシュは、実装が小規模に収まり、Durable Functions や追加のストレージ設計を必要としない場合にのみ、このパスで追加してよい。そうでなければ、キャッシュは保留残課題とするべきである。

## 既知の高リスク境界

詳細なコントラクト分析と最終的なランタイムコントラクト選定は `change-risk-triage.agent.md` に属する。本 Plan は候補の特定のみを行う。

| リスクトリガー                             | 状態         | 境界候補                                                                           |
| ----------------------------------- | ---------- | ------------------------------------------------------------------------------ |
| クロスプロセスまたはクロスサービスシーケンス              | 存在する       | モバイル/ブラウザクライアント → Easy Auth 保護された Azure Function → 外部公開 Web サイト → Azure OpenAI |
| キュー / イベント / Webhook / バックグラウンドワーカー | 必須スコープには不在 | HTTP のみのパスではキュー、Webhook、バックグラウンドワーカーは不要                                        |
| 外部 API または SDK                      | 存在する       | RAKU SPA 公開 Web ページ、補足プレスリリースページ、Azure OpenAI SDK/API                          |
| 認証または承認                             | 存在する       | Easy Auth / Microsoft Entra サインインが Function エンドポイントを保護                         |
| 永続的な状態 / リトライ / リプレイ / 冪等性          | 不明確        | キャッシュまたはスケジュール更新が追加されない限り、永続的な状態は不要                                            |
| スタートアップ配線 / DI / 設定                 | 存在する       | HttpClient、ソースコレクター、AOAI クライアント、バリデーター、オプション、ログ記録                              |
| テスト代替物から分離された本番実装                   | 存在する       | ソースフェッチャーと AOAI 抽出には信頼性の高い検証のためのテスト代替物/フェイクが必要                                 |
| 状態を調整する複数のランタイム参加者                  | 存在する       | クライアント、Easy Auth プラットフォームレイヤー、Function ランタイム、外部 Web サイト、AOAI サービス              |
| 複数コンポーネントにまたがる観測可能な動作               | 存在する       | 最終イベントレスポンスはソース収集、LLM 抽出、検証、選択に依存                                              |

下流トリアージ向けの高リスク境界候補：

1.  Easy Auth で保護された HTTP エンドポイントの動作
2.  Azure OpenAI 構造化抽出スキーマと検証境界
3.  外部 Web サイトのソース収集と決定論的な候補構築
4.  LLM 後の検証とアクティブ/次回イベント選択
5.  設定と本番依存関係の配線

## 今回のパスのスコープ外

*   LLM 画像分析
*   カレンダー画像 OCR またはビジョン抽出
*   Playwright 自動化
*   Chrome 拡張機能の自動化
*   複数施設サポート
*   ネイティブ Android アプリ
*   プッシュ通知
*   実装が明示的に最小限のキャッシュウォームアップを選択しない限り、スケジュールされたバックグラウンドポーリング
*   Durable Functions オーケストレーション

## change-risk-triage への引き継ぎ

`change-risk-triage.agent.md` は、本 Plan を信頼できる情報源として使用し、ランタイムリスクを分類するべきである。

評価すべき主要なスライスは以下のとおり：

1.  **認証付き HTTP アクセス**
    *   Easy Auth の設定と Function の承認レベルの組み合わせは、ブラウザ/モバイルの呼び出し元に対して意図した動作を生成するか？
    *   実装は未認証の呼び出し元へのデータ漏洩を防いでいるか？

2.  **Azure OpenAI 構造化抽出**
    *   スキーマは、信頼性の高い下流検証のためにモデル出力を十分に制約しているか？
    *   検証は、サポートされていないまたはハルシネーションによるイベント候補を拒否するか？

3.  **外部ソース収集**
    *   ソースコレクターは、公式ページの構造変更、取得失敗、フィールドの欠落を、誤解を招く結果を返すことなく処理するか？

4.  **アクティブ/次回イベント選択**
    *   決定論的な選択は、アクティブ、将来、重複、不在のイベントケースに対して正しい結果を生成するか？

5.  **本番配線**
    *   本番の HttpClient、AOAI クライアント、設定、タイムゾーン、認証設定は、実際に Function エントリポイントに配線されているか？
